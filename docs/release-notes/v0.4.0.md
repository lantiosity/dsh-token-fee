<h3 id="cn-v0.4.0">功能</h3>

- **兼容 DSH 的「DeepSeek 账号」路由**：DSH 有两条 DeepSeek 路由——`deepseek-official`（API key，`dsh-llm-deepseek-api-key`）与 `deepseek-account`（账号令牌，`dsh-llm-deepseek-account`，界面里叫「DeepSeek 账号」），base bundle 里默认都启用。两者共用同一套 Messages 传输与同一份模型目录，只有鉴权方式不同；账号侧的模型 id 是 `deepseek-v4-flash` / `deepseek-v4-pro`。此前只有历史路由 `deepseek` 一个别名，账号路由的用量因此整段落进「未配置价格」而从合计里消失。
- 现在 `deepseek-account` 与 `deepseek-official` 命中同一份内置价目；账号侧的真实模型 id 由模型别名（`deepseek-v4-flash` → `deepseek-flash`）接手。别名的语义是「精确命中失败后才回退」，想给账号路由单独定价，按 `provider: "deepseek-account"` 加一条即可，它会优先获胜。
- **中国大陆法定节假日随包发布**：官方定价页写明高峰判定「法定节假日除外」，此前的实现按自然工作日判定，因此 2026 年春节那 9 天（含 2/16–2/20 五个工作日）全部被算成高峰价。现在 `data/cn-holidays.json` 提供 2026 年的 33 天法定节假日与 6 天调休上班，内置 `deepseek` 规则挂上其中的 `cn` 集合，假期不再按高峰计；节假日落在高峰星期时判为空闲。
- **官方口径：调休上班的周末也按空闲计**。内置 `deepseek` 规则因此只挂 `holidays`（排除法定节假日）、**不**挂 `workdays`，调休的周六周日按其所在星期自然落进空闲——这正是官方价。数据里仍然记着 6 天调休，供需要它的场景使用。
- **调度规则新增两个字段**（方向相反、形状相同，都接受集合名或内联日期数组）：`holidays` 里的日期**不算高峰**，`workdays` 里的日期**算高峰**。判定顺序是 `holidays` 优先，其次 `peakDays`/`workdays` 决定是不是高峰日，最后看窗口；同一天同时出现在两张表里时以假期为准。`workdays` 是给「你的提供方确实把调休周末算高峰」这种场景留的通用开关，**按官方价计费时不要给 `deepseek` 挂 `workdays`**。
- 编辑器规则卡片新增「法定节假日」下拉框：选项来自随包数据，值写集合名，落盘保持名字，换一年的数据只需换配置文件。

<h3 id="cn-v0.4.0-fixes">修复</h3>

- **倒计时在长假期会消失**：`nextTariffBoundary` 的逐日推进上限原为 8 天，而 2026 年春节连休 9 天——上限不变的话，从假期第一天起就找不到下一次时段切换，倒计时直接消失。现在有节假日例外时把上限放宽到 32 天（正常规则仍会在头几天提前返回）。
- **测试运行器不等待异步用例**：`test-client.mjs` 的 `test()` 直接调用用例体就计数，而文件末尾的 `process.exit()` 跑在微任务之前——三条 `async` 用例（含「两侧对未定价模型的判定一致」）从来来不及执行，无条件算作通过。它们现在被登记、汇总前统一等待，之前的断言也因此第一次真正生效。

<h3 id="en-v0.4.0">Features</h3>

- **Compatible with DSH's "DeepSeek Account" route**: DSH has two DeepSeek routes — `deepseek-official` (an API key, `dsh-llm-deepseek-api-key`) and `deepseek-account` (an account token, `dsh-llm-deepseek-account`, shown as "DeepSeek Account" in the UI), both enabled by default in the base bundle. They share one Messages transport and one model catalog and differ only in authentication; the account side's model ids are `deepseek-v4-flash` and `deepseek-v4-pro`. Previously only the historical `deepseek` route id was aliased, so the account route's usage fell entirely into "unpriced" and vanished from the total.
- `deepseek-account` now matches the same built-in pricing as `deepseek-official`, with the account side's real model ids handled by the model alias (`deepseek-v4-flash` → `deepseek-flash`). The alias only falls back after an exact match fails, so to price the account route separately just add an entry with `provider: "deepseek-account"` and it wins.
- **Mainland China public holidays ship with the package**: the official pricing page states that the peak decision excludes public holidays, but the earlier implementation decided by natural weekdays, so the 2026 Spring Festival's 9 days (including five weekdays 2/16–2/20) were all priced as peak. Now `data/cn-holidays.json` provides 33 public holidays and 6 make-up workdays for 2026, the built-in `deepseek` schedule references its `cn` set, holidays no longer count as peak, and a holiday falling on a peak weekday is judged off-peak.
- **Official rule: make-up workdays on weekends are priced as off-peak too.** The built-in `deepseek` schedule therefore references `holidays` (excluding public holidays) and **not** `workdays`, so a make-up Saturday or Sunday falls off-peak by its own weekday — exactly the official rate. The data still records the 6 make-up workdays for scenarios that need them.
- **Two new schedule fields** (opposite in direction, identical in shape, each accepting a set name or an inline date array): dates in `holidays` are **not peak**, dates in `workdays` **are peak**. The decision order is `holidays` first, then whether it is a peak day at all (`peakDays` weekdays or `workdays` dates), and only then the window; when one date appears in both tables, the holiday wins. `workdays` is a general switch for providers that do charge peak on make-up weekends — **do not attach it to `deepseek` when matching the official rate**.
- The rule card in the editor gained a "Public holidays" dropdown: the options come from the packaged data, the value is the set name, it is written back by name, and updating a year's data is just swapping the data file.

<h3 id="en-v0.4.0-fixes">Fixes</h3>

- **The countdown vanished across a long holiday**: `nextTariffBoundary` capped the day-by-day scan at 8 days, but the 2026 Spring Festival runs 9 days — with the old cap, the first day of the holiday could not find the next switch and the countdown disappeared. With holiday exceptions the cap is now 32 days (normal rules still return early within the first few days).
- **The test runner never awaited async cases**: `test-client.mjs`'s `test()` invoked the body and counted it immediately, while the file's trailing `process.exit()` ran before the microtasks — three `async` cases (including the host/browser unpriced parity test) never got to run and always counted as passed. They are now registered and awaited before the summary, so those assertions take effect for the first time.
